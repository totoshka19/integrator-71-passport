# Паспорт объекта

Тестовое задание для платформы «Интегратор 7/1». Страница строительного объекта
с тремя вкладками: основные данные, этапы работ и смета.

**Демо:** _ссылка появится после деплоя_

---

## Стек

| | |
|---|---|
| Next.js | 16.3.4, App Router |
| React | 19.2.8 |
| TypeScript | 5, `strict` и ещё шесть флагов строгости |
| Tailwind CSS | 4 (CSS-first, без `tailwind.config`) |
| shadcn/ui | пресет `radix-nova`, 12 примитивов |
| Vitest | 5, jsdom, Testing Library |

Сверх `strict` включены `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
`noImplicitOverride`, `noFallthroughCasesInSwitch`, `noUnusedLocals` и
`noUnusedParameters`. Ни одного `any` в проекте нет.

Данные захардкожены в коде, бэкенда нет. Состояние — `useReducer` и `useState`,
без внешних стор-библиотек.

## Запуск

Нужен **Node 22.12 или новее** — этого требует Vitest. Next.js собирается и на
20.9, но тесты на нём не запустятся. Разработка велась на Node 24.11.

```bash
npm install
npm run dev
```

Откроется на http://localhost:3000 и сразу перенаправит на демонстрационный
объект.

## Что внутри

Два демонстрационных объекта:

| Маршрут | Зачем |
|---|---|
| `/objects/obj_kottedzh-zaozerye` | заполненный: 13 этапов, 8 позиций сметы |
| `/objects/obj_kvartira-mytishchi` | пустой черновик: показывает пустые состояния |

Оба пререндерятся статически через `generateStaticParams`. Корень `/` делает
редирект на первый.

**Вкладка «Основное».** Название, адрес, тип объекта, площадь, статус.

**Вкладка «Этапы работ».** Список этапов с датами и статусом, кнопка смены
статуса у каждого, модальное окно добавления. Названия этапов — реальный цикл
строительства из документа заказчика, а не «Этап 1, Этап 2».

**Вкладка «Смета».** Таблица позиций с итоговой стоимостью, модальное окно
добавления. На ширине меньше 768 px таблица заменяется карточками.

## Ключевые решения

**Вкладки описаны данными, а не разметкой.** В документе заказчика у паспорта
семь разделов, а не три, поэтому набор вкладок задан одним массивом, из которого
выводится тип `TabId`. Добавление четвёртой вкладки — одна строка в массиве;
компилятор потребует для неё панель, потому что `switch` закрыт `assertNever`.

**Статус этапа нельзя выставить, его можно достичь.** В действиях редьюсера нет
варианта «поставить статус» — есть только переход `start` / `complete` /
`reopen`. Правило из документа заказчика («система переходит к следующему этапу
только после подтверждения предыдущего») выражено в проверке перехода, а не в
доступности кнопки: кнопка всегда активна, а при запрещённом переходе объясняет
причину. У поля `status` во всём проекте единственный писатель.

**Производные значения не хранятся.** У позиции сметы нет поля «сумма» — это
произведение количества на цену. Итог, комиссия и доступность перехода
вычисляются при отрисовке. Ошибки форм тоже выводятся из значений, а не лежат в
состоянии: поэтому сообщение исчезает сразу после исправления поля.

**Инварианты живут в конструкторах.** «Количество больше нуля» и «окончание не
раньше начала» проверяются при создании значения, а не только в форме, поэтому
их не обойти ни моками, ни будущим импортом данных.

Приведений типов в рабочем коде ровно два: конструкторы брендов в
`src/lib/scalars.ts` и подделка события `onChange` для react-day-picker в
`calendar-dropdown.tsx` — библиотека читает из него единственное поле.

**Одна директива `"use client"`.** Она стоит в `passport-workspace.tsx` и
помечает границу, а не каждый компонент с обработчиком. Вкладка «Основное»
остаётся серверной: она приходит в клиентский компонент готовым узлом.

**Форматтеры свои, а не `Intl`.** ICU в Node и в браузере расходятся в символе
разделителя разрядов, что даёт расхождение при гидратации. Даты форматируются
разбором строки, без `new Date()` — значит без сдвига на часовой пояс.

## Расхождения ТЗ и документа заказчика

Документ с описанием платформы местами противоречит техническому заданию.
Во всех случаях реализовано **по заданию**, расхождения — ниже.

| | Техническое задание | Документ платформы |
|---|---|---|
| Тип объекта | 4 значения в одном поле | 17 типов строений по 4 независимым осям |
| Квартира, коммерция | есть | отсутствуют, платформа про загородное строительство |
| Статусы объекта | черновик / активный / завершён / архив | активный / завершённый / **на гарантии** / архивный |
| Смета | 4 колонки | 10 полей: НДС, комиссия, страховка, логистика |
| Разделы паспорта | 3 вкладки | 7 разделов |

Две вещи из документа всё же добавлены, потому что без них интерфейс теряет
смысл:

- **колонка «Ед. изм.»** — без неё «120» в смете ничего не означает;
- **строка «Комиссия платформы 7%»** в блоке итогов.

Обе изолированы намеренно: удаление одной строки в `ESTIMATE_COLUMNS` и одного
блока в `estimate-tab.tsx` возвращает смету ровно к четырём колонкам задания,
функция расчёта итога при этом не меняется.

## Чего сознательно нет

Слоёв FSD и barrel-файлов — доменная область одна. Библиотек форм и схем
валидации — две формы по три-четыре поля не окупают двух зависимостей.
Контекста, стора и мемоизации — глубина проброса пропсов два уровня, а 13 этапов
не тот объём, который мемоизируют. Синхронизации вкладок с URL, авторизации и
`localStorage` — прямые ограничения задания. Ничего из документа заказчика сверх
двух названных мелочей: ни НДС, ни ролей, ни семи разделов.

## Тесты

```bash
npm test
```

166 тестов. Логика вынесена в чистые функции без React, поэтому большая часть
проверяется без DOM; интерфейс покрыт интеграционными сценариями через
Testing Library — добавление этапа и позиции, запрет перехода, сохранение
состояния при переключении вкладок.

```
Statements   97.18%
Branches     92.59%
Functions      100%
Lines        98.26%
```

Непокрытыми осознанно оставлены ветки `assertNever` и защитные проверки,
недостижимые по построению: чтобы их выполнить, пришлось бы подделывать
невозможные состояния.

## Структура

```
src/
├── app/                          маршруты App Router
│   ├── page.tsx                  редирект на демо-объект
│   └── objects/[objectId]/       страница паспорта и её 404
├── components/ui/                примитивы shadcn, руками не правятся
├── features/passport/
│   ├── data/                     имитация API
│   ├── model/                    домен: типы, словари, правила, расчёты
│   │                             чистый TypeScript, без импортов React
│   └── ui/                       компоненты паспорта
└── lib/                          примитивы с проверкой и форматтеры
```

Граница между `model/` и `ui/` видна по дереву: в `model/` нет ни одного импорта
из React, поэтому вся доменная логика тестируется без окружения браузера.
